## Architecture

The system runs three Docker containers orchestrated via `docker-compose`:

- **Router** — lightweight Flask load balancer on port `8082`, routes traffic to backends using odd/even user ID splitting for A/B tests
- **Backend A & B** — two model inference servers, each on port `5001` inside the Docker network

The API endpoint served to the platform:
```
GET /recommend/<userid>
→ Returns ordered comma-separated list of up to 20 movie IDs
→ SLA: respond within 800ms
```

**Key files:**
- [`docker-compose.yml`](docker-compose.yml) — 3-service compose setup
- [`Dockerfile`](Dockerfile) — single image used by all backends
- [`router.py`](router.py) — load balancer with user routing logic
- [`app/main.py`](app/main.py) — Flask inference server with hot-reload

## Data

Data is consumed from an Apache Kafka event stream (`movielog8`) and stored as Parquet:

| File | Schema | Description |
|---|---|---|
| `ratings.parquet` | `[timestamp, user_id, movie_id, rating]` | Explicit user ratings (1–5 stars) |
| `watches.parquet` | `[user_id, movie_id, timestamp_start, timestamp_end, minutes_watched]` | Aggregated watch sessions |
| `movies.parquet` | `[movie_id, title, tmdb_id, imdb_id, release_date, genres, runtime, vote_average, ...]` | Movie metadata |
| `users.parquet` | `[user_id, age, occupation, gender]` | User demographic information |

**Scale:** 10 million Kafka stream events processed.  
**Watch signal:** If a user watches >50% of a movie's runtime, a proxy rating of 3 is assigned to signify interest.

**Data documentation:** [`DATA_DOCUMENTATION.md`](DATA_DOCUMENTATION.md)  
**Ingestion pipeline:** [`data-pull/data_pull.py`](data-pull/data_pull.py)  
**Hourly ingestor:** [`data-pull/hourly_data_pull.py`](data-pull/hourly_data_pull.py)

## Models

### Model 1: Content-Based Filtering *(deployed in production)*

Builds a movie feature matrix and a user preference vector. Recommendations are generated by computing cosine similarity between the user profile and all movie feature vectors.

**Features used:**
- Movie metadata: genre (one-hot), language, budget, revenue, runtime, popularity, vote average/count, release year, overview length, production company/country counts
- User metadata: age, gender
- Interaction signals: ratings + watch-time proxy ratings

**Cold-start handling:** New users are matched to the most demographically similar existing user; their profile is adopted until sufficient interaction history accumulates.

**Why chosen:** Superior accuracy (14.49% precision) vs. the hybrid model (0.15%). Better catalog coverage (37% vs 1%) and strong NDCG (0.1523).

**Implementation:** [`app/model/src/content_based.py`](app/model/src/content_based.py)

---

### Model 2: Hybrid Recommender (Content-Based + Collaborative Filtering)

Combines a genre-weighted content score with a user-item collaborative filtering score into a normalized weighted sum. Cold-start handled by sampling from the top-100 most popular movies.

**Why not chosen for production:** Despite faster training (0.83s vs 297s), precision was 94x lower than Model 1.

| Metric | Model 1 (Content-Based) | Model 2 (Hybrid) |

## Evaluation

### Offline Evaluation

**Strategy:** Temporal train/test split (80/20) — all test interactions occur strictly after training data (split timestamp: `2025-10-24 04:17:34`) to prevent data leakage.

**Primary metric:** Recall@20 — proportion of items a user actually engaged with that appear in the top-20 recommendations. Recall is preferred over precision because the average user has ~1 interaction in the test set, making precision uninformative.

**Results:**

| Metric | Value |
|---|---|
| Recall@20 | 46.53% |
| Precision@20 | 2.33% |
| NDCG@20 | 0.2805 |
| Hit Rate@20 | 46.58% |
| Diversity | 0.90 |
| Coverage | 45.55% |

**Implementation:** [`app/model/offline_evaluation.py`](app/model/offline_evaluation.py)  
**Results:** [`app/model/offline_evaluation_results.json`](app/model/offline_evaluation_results.json)

## Deployment & Containerization

The inference service is containerized and deployed via Docker Compose with **zero-downtime hot-reload**:

- A file watcher (watchdog/inotify) monitors `./app/pkl_models/` for new model artifacts
- On detection, `_swap_model()` in `app/main.py` atomically replaces the in-memory model without restarting the container
- Fallback: polling-based watcher if inotify is unavailable (`WATCHDOG_FORCE_POLLING=1`)

**Environment variables:**
```
BACKEND_NAME      — identifies backend instance (a or b)
MODEL_TAG         — selects which model artifact to load
MODEL_WATCH_INTERVAL  — polling interval in seconds (default: 1.0)
WATCHDOG_FORCE_POLLING — skip inotify, use polling
```

### Alerting (3-tier hierarchy)

**Service (fast response):**
- `ServiceDown` — service unavailable for >2 min
- `HighErrorRate` — error rate >5% over 5 min
- `HighLatencyP95` — p95 latency >1s for 10 min

**Model (noise-resistant, 30–60 min windows):**
- `LowPrecisionWarmCohort`, `LowNDCGAllUsers`, `ZeroHitRate`

**Drift & pipeline (preventive):**
- `LowDiversityDrift` — diversity drops ≥50% vs 6 hours prior
- `RetrainStale` — no successful retrain in 24 hours

## A/B Experimentation

**Infrastructure:** [`app/model/src/experimentation_infrastructure/`](app/model/src/experimentation_infrastructure/)

**User split:** Odd user IDs → Backend A, Even user IDs → Backend B. This ensures each user is always served by the same model, preserving sample independence.

**Quality metric:** Precision@20 — proportion of top-20 recommendations that users actually engaged with (rated or watched) within 7 days of the recommendation.

**Statistical test:** Bootstrap resampling (10,000 iterations), 2-sided test at α=0.05.

**Results (Model A trained 11/13 vs Model B trained 11/14):**
- Bootstrap p-value: **0.4903** — no statistically significant difference
- Confidence interval: [-0.00, -1.21] — any true difference is very small
- Interpretation: one additional day of training data does not meaningfully improve recommendation quality

**Results file:** [`outputs/ab_test_results.json`](outputs/ab_test_results.json)

## Automated Retraining

**Schedule:** Daily cron at 7:03 PM, retraining on the most recent 4 hours of interaction data.

**Pipeline:**
1. Hourly Kafka ingestor writes partitioned Parquet under `data-pull/hourly_data/date=/hour=/`
2. `merge_hourly_data.py` combines and deduplicates the configured window
3. DVC hashes the data and pushes to Azure Blob Storage
4. `train.py` retrains with parameters from `params.yaml`
5. New model saved to `archive/model_store/model_{tag}_{timestamp}.pkl`
6. Atomic copy to `app/pkl_models/` triggers hot-reload in the running containers — **no downtime**

**Key files:**
- [`scripts/retrain_cron.sh`](scripts/retrain_cron.sh)
- [`data-pull/merge_hourly_data.py`](data-pull/merge_hourly_data.py)
- [`params.yaml`](params.yaml)

## Provenance Tracking

Every trained model embeds full provenance metadata queryable at inference time:

| Metadata Field | Description |
|---|---|
| `model_tag` | Version identifier |
| `trained_at` | Training timestamp |
| `git_commit_hash` | Pipeline code version |
| `pipeline_version` | From `params.yaml` |
| `data_hash` | DVC hash of training data |
| `data_start_timestamp` | Earliest data point used |
| `data_end_timestamp` | Latest data point used |

**To trace any past prediction:**
1. Look up the `trained_at` timestamp in the prediction log (`app/logs/predictions_*.jsonl`)
2. Load the corresponding model from `archive/model_store/`
3. Query `model.metadata` for git hash, data hash, and time window
4. Use the DVC data hash to pull the exact training slice from Azure Blob Storage

## Fairness Analysis

**Protected attributes:** Gender, Age

**Fairness requirement:** Demographic parity — Recall@20 disparity between Men and Women must be <5%.

**Results (619,657 men vs 127,398 women):**

| Group | Mean Recall@20 |
|---|---|
| Men | 7.75% |
| Women | 7.43% |

**Absolute disparity: 0.31%** — well below the 5% threshold. The model passes the demographic parity requirement.

**Mitigation strategies proposed:**
- Max Fairness hyperparameter tuning (optimize for worst-off demographic rather than global average)
- Interactive onboarding taste test to replace demographic-based cold-start profiling

**Implementation:** [`app/model/src/experimentation_infrastructure/fairness_evaluator.py`](app/model/src/experimentation_infrastructure/fairness_evaluator.py)

## Feedback Loop Analysis

**Two anticipated feedback loops:**

**1. Popularity Reinforcement / Exposure Concentration Loop**  
Highly recommended items gain more exposure → more interactions → stronger training signal → recommended even more. Evidence found in 7-day analysis: top-50 items occupied **94–95%** of all recommendation slots, with top-1% share at **96–97%**.

**2. Representation Skew / Genre-Era Narrowing Loop**  
Under-represented genres receive fewer interactions → weaker training signal → recommended even less → persistent under-exposure for niche content.

**Mitigation: Diversity-Guided Re-Ranking**  
A post-processing re-ranking step applies an exposure penalty to items that appear disproportionately in recent recommendation logs, without modifying the underlying model.

**Analysis script:** [`scripts/feedback_loop_analysis.py`](scripts/)

## Security Analysis

**Threat model:** STRIDE framework applied to all system components.

**Issue 1: Pickle Deserialization Attack (CRITICAL)**  
The hot-reload mechanism automatically loads `.pkl` files. A malicious pickle file placed in `/app/pkl_models/` executes arbitrary code on load.  
*Mitigations:* Replace pickle with ONNX, implement HMAC-SHA256 signature verification, sandbox model loading in a restricted container.

**Issue 2: No Authentication (HIGH)**  
Zero authentication enables DoS, user enumeration, and privacy attacks.

**Attacks detected in production logs (Nov 16–19, 2025):**
- **DoS attack detected** — peak 972 req/min (8.5x normal), sustained 5 consecutive minutes
- **Privacy attack detected** — 3 users with anomalously high request counts consistent with profiling
- **User enumeration detected** — 13 time windows with >80% unique user diversity ratio (normal: 77%)

*Mitigations:* API key / JWT authentication, rate limiting via Flask-Limiter + nginx, infrastructure-level DDoS protection.

**Analysis:** [`analysis/run_security_analysis.py`](analysis/run_security_analysis.py)  
**Results:** [`analysis/security_analysis_results.json`](analysis/security_analysis_results.json)

## CI/CD

**Platform:** GitHub Actions ([`.github/workflows/ci.yml`](.github/workflows/ci.yml))

**Triggers:** Every push and pull request to `main`

**Steps:**
1. Checkout repository
2. Set up Python 3.10
3. Install runtime deps (`requirements.txt`) and test deps (`tests/requirements-dev.txt`)
4. Run full test suite with coverage:
```bash
pytest --maxfail=1 --disable-warnings tests \
  --cov=app --cov=data_pull \
  --cov-report=term-missing \
  --cov-report=xml:coverage.xml \
  --cov-report=html:coverage_html
```
5. Upload coverage artifacts (XML + HTML) to GitHub Actions

**Branch protection:** `main` is a protected branch. All changes require a PR reviewed and approved by at least one team member before merging.

**Deployment:** A GitHub PAT on the VM pulls the latest passing build and restarts the service via a lightweight update script.
